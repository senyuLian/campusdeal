## 方案 A：全能型·双核心方案

### 一句话定位
"从高并发秒杀到 AI 智能助手，完整 O2O 平台的现代技术栈。"

### 技术架构

```
                    ┌──────────────────────────┐
                    │     Nginx (静态+反向代理)   │
                    └──────────┬───────────────┘
                               │
                    ┌──────────▼───────────────┐
                    │   Spring Boot 3.1 (8081) │
                    └──────────────────────────┘
           ┌────────────────────┼────────────────────┐
           │                    │                     │
    ┌──────▼──────┐    ┌───────▼───────┐    ┌───────▼───────┐
    │  秒杀模块    │    │  常规业务模块  │    │  智能助手模块   │
    │             │    │              │    │              │
    │ Caffeine L1 │    │ 店铺搜索/推荐  │    │ LangGraph4j  │
    │ Redis L2    │    │ 笔记/关注/签到 │    │ ReAct Agent  │
    │ Kafka 异步   │    │ 优惠券管理     │    │ Function Call │
    │ Canal 同步   │    │              │    │ SSE 流式输出  │
    └─────────────┘    └──────────────┘    └──────────────┘
           │                                        │
    ┌──────▼──────┐                         ┌──────▼──────┐
    │   MySQL     │                         │  LLM API    │
    │   Redis     │                         │  (通义/DeepSeek) │
    └─────────────┘                         └─────────────┘
```

### 核心工作（在现有 campusdeal 上新增）

#### 第一部分：秒杀链路升级（不可变造，要能面试展示）

| 功能点 | 具体内容 | 面试可讲 |
|---|---|---|
| **多级缓存** | Caffeine 本地缓存 → Redis 分布式缓存 → MySQL，逐级降级 | "缓存击穿/穿透/雪崩的完整方案" |
| **布隆过滤器** | 预热时加载所有秒杀券 ID，拦截非法请求 | "如何在海量请求中快速过滤无效流量" |
| **Redis + Lua 原子扣库存** | 单次 Lua 脚本完成库存校验+扣减+一人一单校验 | "为什么 Lua 能保证原子性" |
| **Kafka 异步落库** | 秒杀成功后发 Kafka 消息，异步写 MySQL | "削峰填谷的具体实现" |
| **消费端幂等** | 基于 Redis 幂等表 + MySQL 唯一索引双重保障 | "为什么不能只用一种幂等方案" |
| **最终一致性** | 本地消息表 + 定时任务补偿 | "分布式事务的方案选型对比" |
| **Canal binlog 异步刷新** | 监听 MySQL 变更，自动失效 Redis 缓存 | "缓存一致性问题的解决思路" |
| **集群 hash tag 路由** | 秒杀库存 key 和订单 key 落在同一 Redis slot | "Redis Cluster 下的跨 slot 问题" |

#### 第二部分：智能助手 Agent

| 功能点 | 具体内容 | 面试可讲 |
|---|---|---|
| **LangGraph4j 状态图** | 条件边约束行为边界，兜底转人工 | "为什么用状态图而不是链式调用" |
| **Function Call** | 订单查询、退款、核销、店铺搜索作为 Tool | "工具定义的 schema 设计原则" |
| **ReAct 循环** | 推理→行动→观察闭环 | "ReAct vs Plan-and-Execute 的选择" |
| **SSE 流式输出** | 前端逐字渲染 LLM 回复 | "SSE vs WebSocket vs 轮询" |
| **二级确认** | 退款/下单等操作画二次确认弹窗 | "Agent 安全性设计" |
| **Prompt 注入检测** | 关键词匹配 + 语义检测 | "安全防护分层策略" |
| **PII 脱敏** | 手机号/身份证自动打码 | "数据安全合规" |

### 面试亮点（一句话版本）

1. 多级缓存 + 布隆过滤器 + Canal 组成了完整的"缓存→数据库"一致性闭环
2. Redis + Lua 原子操作 + Kafka 异步削峰，TPS 从 ~500 提升到 ~50000
3. LangGraph4j 状态图编排 Agent，条件边约束行为边界 + 兜底转人工
4. 消费端幂等表 + 本地消息表双保险，保证最终一致性

### 适合谁
- 目标是大厂通用后端岗位（阿里/字节/美团/快手）
- 想要"广度"——面试时什么话题都能聊
- 喜欢做完整系统，不排斥写较多代码

## 方案 B：AI Agent 深度型方案

### 一句话定位
"基于 LangGraph4j 的多 Agent 协作智能助手系统，结合 RAG 和知识图谱的 O2O 行业解决方案。"

### 技术架构

```
                        用户（Web/小程序）
                              │
                    ┌─────────▼─────────┐
                    │   API Gateway     │
                    │   (SSE 流式输出)   │
                    └─────────┬─────────┘
                              │
              ┌───────────────▼───────────────┐
              │      Router Agent             │
              │  (意图识别 + 路由 + 降级)      │
              └───────────────┬───────────────┘
                              │
        ┌─────────┬───────────┼───────────┬─────────┐
        ▼         ▼           ▼           ▼         ▼
  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
  │ 订单    │ │ 优惠券   │ │ 店铺    │ │ 退款    │ │ 人工    │
  │ Agent   │ │ Agent   │ │ Agent   │ │ Agent   │ │ 客服    │
  └────┬────┘ └────┬────┘ └────┬────┘ └────┬────┘ └─────────┘
       │           │           │           │
       └───────────┴─────┬─────┴───────────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
  ┌──────────┐   ┌──────────────┐   ┌──────────┐
  │ 工具调用  │   │  RAG 检索     │   │ 知识图谱  │
  │ Function │   │  (混合检索)   │   │ (Neo4j) │
  │  Call    │   └──────────────┘   └──────────┘
  └──────────┘
```

### 核心新增（秒杀部分维持在现有 campusdeal 水平）

#### Agent 深度构建

| 模块 | 内容 | 亮点 |
|---|---|---|
| **Router Agent** | 高频意图用小模型（预分类），复杂意图路由大模型 | 成本优化，首 token 延迟低 |
| **多 Agent 协作** | 5 个领域 Agent，通过 Agent 间消息传递共享上下文 | 类 Prime Agent 的 `agent_message` 模式 |
| **RAG 混合检索** | BM25（关键词）+ Embedding（语义），结果融合排序 | 召回率高，回答精准 |
| **知识图谱** | Neo4j 存储"店铺→优惠券→适用条件"等关系 | 复杂查询（"我有 XX 券，附近哪些店能用"） |
| **前缀缓存** | 复用固定系统 prompt + 工具定义的 token 前缀 | API 成本降低 30-50% |
| **多层导航上下文** | 默认给摘要+引用，Agent 判断需要时拉完整内容 | 避免 Token 浪费 |
| **幻觉溯源** | 每个结论附带来源引用（RAG 文档/Markdown 片段/数据库记录） | 可验证，面试加分 |
| **小模型路由** | 简单 FAQ 命中缓存直接返回，不调 LLM | 成本和延迟双优 |
| **对话分支树** | 基于 prime-agent 分析文档的会话模型 | "重新回答"可追溯 |

#### 秒杀部分（作为"现有系统基础"，不做大幅改动）

- 维持现有 Redisson 分布式锁 + Redis 库存预扣
- 新增一个简单的"秒杀结果查询"作为 Agent 工具的展示案例
- 可选：加一个 Bloom filter 作为面试话题

### 面试亮点

1. 多 Agent 协作架构：5 个领域 Agent + Router，Agent 间消息传递
2. RAG 混合检索：BM25 + 向量语义，融合排序，可溯源的回答
3. 知识图谱解决复杂关联查询（店铺×券×用户×地理位置）
4. 从意图识别→模型路由→工具调用→结果验证的完整闭环
5. Token 成本控制四件套：前缀缓存 + 多层导航 + 小模型路由 + 滑动窗口

### 适合谁
- 目标是大厂 AI 应用/AI 平台/大模型相关岗位
- 对 Agent 架构、RAG、LLM 感兴趣
- 想要"深度"——在一个方向上打得很深

## 方案 C：分布式系统深度型方案

### 一句话定位
"十万级 TPS 秒杀系统的完整设计与实现——从缓存架构到消息驱动最终一致。"

### 技术架构

```
  用户请求
     │
     ▼
┌─────────────┐   miss   ┌─────────────┐   miss   ┌──────────┐
│ Caffeine L1 │─────────▶│  Redis L2    │─────────▶│  MySQL   │
│ (本地缓存)   │          │ (分布式缓存)  │          │ (持久化)  │
└─────────────┘          └─────────────┘          └──────────┘
       ▲ hit                    ▲                      │
       │                        │ cache aside          │ binlog
       │                        │                      ▼
       │                 ┌─────────────┐        ┌────────────┐
       │                 │ Bloom Filter │        │   Canal    │
       │                 │ (防穿透)      │        │ (binlog订阅)│
       │                 └─────────────┘        └────────────┘
       │                                               │
       │                                         缓存失效通知
       │                                               │
       └───────────────────────────────────────────────┘

秒杀链路：

  请求 → 布隆过滤器 → Redis+Lua原子扣库存 → Kafka异步消息
                                                     │
                              ┌──────────────────────┘
                              ▼
                      ┌──────────────┐
                      │ 消费端幂等校验 │
                      │ (Redis+MySQL) │
                      └──────┬───────┘
                             │
                      ┌──────▼───────┐
                      │  订单落库     │
                      │ (本地消息表)  │
                      └──────┬───────┘
                             │
                      ┌──────▼───────┐
                      │  定时补偿     │
                      │ (最终一致)    │
                      └──────────────┘
```

### 核心工作

#### 秒杀系统极致深化

| 层级 | 技术点 | 面试深度 |
|---|---|---|
| **前端/网关** | Nginx 限流（limit_req_zone）+ 秒杀 URL 动态化 | 动静分离方案 |
| **接入层** | 布隆过滤器拦截非法券 ID + 用户频控（Redis 滑动窗口） | 误判率计算、布隆不能删除的替代方案 |
| **本地缓存 L1** | Caffeine 库存标记（有/无）+ TTL 自动刷新 | W-TinyLFU 淘汰策略原理 |
| **分布式缓存 L2** | Redis Cluster hash tag 同 slot 路由 | 为什么库存+订单要在同一 slot |
| **原子操作** | Lua 脚本：检查库存 → 检查重复 → 扣减 → 记录 | Lua 在 Redis 中的原子性保证 |
| **削峰** | Kafka 异步落库，分区键 = user_id（保序） | Kafka 分区策略选择 |
| **幂等** | Redis 幂等表（快速去重）+ MySQL 唯一索引（兜底） | 双重幂等的必要性 |
| **最终一致** | 本地消息表 + 定时任务扫描补偿 | 与 RocketMQ 事务消息的对比 |
| **缓存一致** | Canal 监听 binlog → 失效 Redis 缓存 | 与先更新 DB 再删缓存的对比 |
| **灰度发布** | 秒杀页面静态化 + CDN + 逐台发布验证 | 发布策略与回滚 |

#### 智能助手（轻量版本）

| 功能 | 简化方案 |
|---|---|
| Agent 框架 | 仅做一个简单的 ReAct Agent（不需要多 Agent） |
| 工具 | 3-4 个工具：查店铺、查订单、查券、模拟退款 |
| RAG | 不做复杂检索，仅做 FAQ 向量检索 |
| 输出 | SSE 流式回复 |

### 面试亮点

1. "从浏览器到数据库"的全链路优化方案，每层都有明确的技术选型理由
2. Redis + Lua 原子操作实现零超卖的库存扣减，压测数据支撑
3. Kafka + 幂等 + 本地消息表的最终一致性方案选型对比
4. Canal binlog 订阅实现缓存与数据库的最终一致性
5. 系统可压测可验证：JMH 做单元压测，JMeter 做接口压测，给出 TPS 对比数据

### 适合谁
- 目标是大厂基础架构 / 中间件 / 分布式系统方向
- 对秒杀、缓存、消息队列、分布式事务有深度理解
- 喜欢"硬核"后端，用压测数据说话
- Agent 只是锦上添花，不作为主亮点

│  └───────────────┘   │  └──────────────────────┘    │
│                       │                              │
│  ┌───────────────┐   │  ┌──────────────────────┐    │
│  │ 优惠券管理     │   │  │ 智能券推荐 Agent      │    │

│  └───────────────┘   │  └──────────────────────┘    │
│                       │                              │
│  ┌───────────────┐   │  ┌──────────────────────┐    │
│  │ 探店笔记       │   │  │ 内容理解 Agent        │    │
│  │ (Feed/点赞)   │◄──┤  │ 笔记摘要 + 标签生成     │    │
│  └───────────────┘   │  └──────────────────────┘    │
│                       │                              │
├───────────────────────┼──────────────────────────────┤
│  数据层               │  AI 基础设施                  │
│  ┌─────────────────┐  │  ┌──────────────────────┐    │
│  │ MySQL + Redis   │  │  │ 知识图谱 (Neo4j)      │    │
│  │ + Kafka + Canal │  │  │ 店铺→券→笔记→用户关系  │    │
│  └─────────────────┘  │  └──────────────────────┘    │
│                       │  ┌──────────────────────┐    │
│                       │  │ RAG 检索引擎          │    │
│                       │  │ BM25 + Embedding + KG │    │
│                       │  └──────────────────────┘    │
└─────────────────────────────────────────────────────┘

### 核心工作

#### 特色一：知识图谱驱动的智能推荐

```
Neo4j 建模：
  (User)-[:LIKES]->(ShopType)
  (Shop)-[:BELONGS_TO]->(ShopType)
  (Shop)-[:OFFERS]->(Voucher)
  (Voucher)-[:REQUIRES]->(Condition)
  (Blog)-[:ABOUT]->(Shop)
  (User)-[:WROTE]->(Blog)

Agent 查询示例：
  "我有两张 XX 店的优惠券，附近还有类似的店吗？"
  → Cypher: MATCH (u:User)-[:HAS_VOUCHER]->(v:Voucher)-[:BELONGS_TO]->(s:Shop)-[:BELONGS_TO]->(t:ShopType)
            MATCH (other:Shop)-[:BELONGS_TO]->(t)
            WHERE distance(s.location, other.location) < 5000
            RETURN other
  → 结合 LLM 生成自然语言推荐理由
```

#### 特色二：RAG 混合检索

```
查询："XX 店的优惠券使用条件是什么？"

  用户 query
       │
       ├─ BM25 检索 ──────► 关键词命中结果
       │                    (Voucher 的 rules 字段)
       │
       ├─ Embedding 相似度 ─► 语义相近结果
       │                    (店铺介绍、笔记内容)
       │
       └─ 知识图谱查询 ────► 结构化关联
                            (店铺→券→条件路径)

  融合排序 (RRF: Reciprocal Rank Fusion)
       │
       ▼
  LLM 生成答案 + 来源引用
```

#### 特色三：演进路径叙事

这个方案最大的面试优势是"讲故事"：

```
v1.0：传统 Spring Boot Web 应用（现有 campusdeal）
  ↓
v2.0：引入 Redis 缓存 + 秒杀优化（高并发改造）
  ↓
v3.0：引入智能助手（单 Agent + Function Call）
  ↓
v4.0：引入知识图谱 + RAG（检索增强）
  ↓
v5.0：多 Agent 协作 + 个性化推荐（AI-Native）

每一版都有明确的动机、技术方案、取舍和效果
面试官听到的是"我知道每个阶段为什么这样做"而不是"我堆砌了技术"
```

### 面试亮点

1. 完整的系统演进路径，展示"从单体到 AI-Native"的架构视野
2. Neo4j 知识图谱解决"关系型数据库做不了"的复杂关联查询

## 我的建议

### 如果目标是大厂通用后端（阿里/字节/美团）
→ **选 A 方案**，但优先做秒杀部分。面试中"高并发秒杀"是 80% 的问题来源，"Agent"是 20% 的差异化加分项。

### 如果目标是 AI 应用/大模型相关岗位
→ **选 B 方案**，Agent 深度决定面试深度。多 Agent + RAG + 知识图谱一起上。

### 如果目标是分布式系统/基础设施岗位
→ **选 C 方案**，秒杀做到能出压测报告的程度。一个有数据的系统比一个有概念的系统强十倍。

### 如果目标是架构师/技术专家方向
→ **选 D 方案**，演进路径的叙事能力是高级岗位的核心竞争力。

### 如果只有一个项目放简历上
→ **选 A 方案**，广度和深度的最佳平衡点。
