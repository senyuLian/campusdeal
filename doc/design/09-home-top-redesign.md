# 设计文档 09：首页顶部两排按钮重设计（CampusDeal 主题）

> 所属 Phase：Phase 3 收尾（前端体验打磨）
> 模块定位：重设计主站首页顶部**搜索栏 + 分类宫格**两排按钮，把首页从"通用生活服务 App 首页"改造为贴合 **CampusDeal 校园生活服务平台** 主题的入口区
> 依赖关系：依赖 07-前端重构产出的 SPA 基础设施（CSS 变量 / Store / Api 层），依赖后端既有接口（详见 §5），不新增后端接口（除可选的数据初始化 SQL）

### 1.2 问题清单

| 编号 | 问题 | 具体表现 | 影响 |
|------|------|----------|------|
| P01 | **搜索框不可用** | `<input disabled>`，纯摆设 | 用户无法检索商户，核心诉求缺失 |
| P02 | **城市定位是死的** | "杭州"写死，不可切换、不携带坐标 | 与校园场景不符；`/merchant/of/type` 的 `x/y` GEO 参数永远无法使用，"附近商户"能力被废弃 |
| P03 | **分类与校园场景脱节** | 当前 10 类：美食/KTV/酒吧/美容SPA/轰趴馆/按摩足疗/美睫美甲/丽人美发/亲子游乐/健身运动 | 明显是"城市泛生活"分类；校园高频场景（奶茶、打印、超市、快递、自习室）完全缺失 |
| P04 | **没有功能入口** | 顶部只有头像跳个人页，分类只跳商户列表 | CampusDeal 的五大模块（**限时抢购 / 附近商户 / 优惠卡券 / 校园动态 / 智能助手**）在首页顶部**零入口**，全靠底部导航（仅有 首页/智能助手/发帖/我的） |
| P05 | **视觉无校园属性** | 通用蓝色主题 + 无品牌露出 | 与"校园平台"定位不符 |

### 1.3 重设计目标

> 一句话：**把顶部两排改造成 CampusDeal 的"功能主入口 + 校园场景分流器"——第一排提供校园定位与搜索，第二排上半提供五大高频功能入口（金刚区：抢购 / 附近 / 卡券 / 动态 / 签到）、下半提供校园场景分类宫格；智能助手保持在页面最下方底部导航，顶部不重复。每个按钮都有真实的后端落点。**

## 2. 第一排「Campus 搜索操作区」详细设计

### 2.1 布局与组件

| 位置 | 组件 | 现状 → 新设计 | 落点 |
|------|------|----------------|------|
| 左侧 | **校园定位** | "杭州"静态 → **校区切换按钮**，显示当前校区（默认"校本部"），点击弹校区选择底部弹层 | `localStorage.campus` 持久化；为附近/GEO 提供坐标 |
| 中部 | **搜索框** | disabled → **可用的智能搜索框**，聚焦展开"热词 + 搜索历史"面板 | 见 §2.2 |
| 右侧 | **个人中心** | 仅 👤 头像 → **保持现状，仅 👤 个人中心**（签到、助手已移至他处，见 §2.4） | `/profile` |

### 2.2 搜索框交互设计

**搜索触发目标（三种命中，优先级从高到低）：**

| 优先级 | 搜索类型 | 判断 | 落点接口 |
|--------|----------|------|----------|
| 1 | **商户名模糊搜索** | 关键词命中商户名 | `GET /merchant/of/name?name={kw}&current=1` |
| 2 | **分类直达** | 关键词命中分类名（如"美食""奶茶"） | `GET /merchant/of/type?typeId={id}&name={kw}` |
| 3 | **无结果兜底** | 前两者均无结果 | 引导到智能助手：跳 `/chat?q={kw}` 自动追问 |

**交互流程：**

```
点击搜索框（聚焦）
   │
   ├─ 展开「搜索面板」：
   │    ├─ 热词（前端内置，与校园场景绑定）：
   │    │    奶茶 / 打印 / 自习室 / 夜宵 / 快递
   │    └─ 最近搜索（localStorage.searchHistory，最多 10 条，可清空）
   │
   ├─ 输入关键词 + 回车 / 点「搜索」
   │    ├─ 写入 searchHistory（去重、最新在前）
   │    ├─ 关闭面板，跳转搜索结果页
   │    └─ 落点：新增路由 `/search?kw={kw}`（复用商家卡片，列表模式）
   │
   └─ 点「清空」/ 点击遮罩 → 收起面板
```

**搜索面板关键词防抖**：输入时不做实时搜索（避免无谓请求），仅回车/点击触发，保证接口低频。

### 2.3 校园定位设计

**数据模型**（前端静态配置，不依赖后端）：

```js
// Store 内新增 campus.js 或并入 store.js
const CAMPUSES = [
  { id: 'main', name: '校本部',     lat: 30.275, lon: 120.155 },
  { id: 'east', name: '东校区',     lat: 30.290, lon: 120.190 },
  { id: 'west', name: '西校区',     lat: 30.260, lon: 120.130 },
];
```

- 当前校区存 `localStorage.campus = {id, name}`，默认 `main`。
- 点击校区按钮 → 底部弹层选择 → 更新 `Store.campus`，写入 localStorage。
- **坐标消费**：所有带 `x/y` 的 GEO 请求（金刚区「附近商户」、分类宫格跳转时可选携带）取 `Store.campus.lon/lat`。
- 校区切换后**不强制刷新页面**；「附近商户」类列表在下次打开时读到新坐标即可。

### 2.4 右侧仅保留「个人中心」

右侧功能区**保持现状**：仅 👤 个人中心（→ `/profile`），本次重设计不在顶部新增其他按钮。

- 📅 **签到**：移入第二排金刚区**第 5 位**（见 §3.1），带连续天数角标。
- 🤖 **智能助手**：保持在**页面最下方**底部导航（foot-bar）入口，不在顶部重复出现，避免入口冗余。

## 3. 第二排「服务金刚区 + 校园分类宫格」详细设计

### 3.1 服务金刚区（Row 2，5 大模块入口）

一行 5 列，图标 + 文案，点击进入 CampusDeal 核心模块：

| # | 入口 | 图标 | 文案 | 落点 | 登录 | 后端接口 |
|---|------|------|------|------|------|----------|
| 1 | 限时抢购 | ⚡ | 抢购 | 闪购专区页（新路由 `/flash`） | 否 | `GET /coupon/flash/list`（新增，见 §5.2） |
| 2 | 附近商户 | 📍 | 附近 | `/shops/nearby?lat=&lon=`（新路由，GEO 列表） | 否 | `GET /merchant/of/type?typeId=&current=1&x={lon}&y={lat}` |
| 3 | 优惠卡券 | 🎟️ | 卡券 | 卡券中心页（新路由 `/coupons`） | 是 | `GET /coupon/list/all`（新增，见 §5.2） |
| 4 | 校园动态 | 🔥 | 动态 | 返回首页帖子流并锚定到 Feed 区 | 否 | `GET /post/hot?current=1` |
| 5 | 每日签到 | 📅 | 签到 | 点击弹签到结果（已签/成功），角标显示连续天数 | 是 | `POST /user/sign`、`GET /user/sign/count` |

> 说明：**智能助手不再占用金刚区**，其入口保持页面最下方底部导航（foot-bar）第 2 位「智能助手」，与顶部无重复。

**落点路由需求（需新增 3 个页面）：**

| 新路由 | 页面 | 说明 |
|--------|------|------|
| `/flash` | FlashDealPage | 全站正在进行的闪购券平铺列表（含商户名、折扣、倒计时、秒杀按钮） |
| `/shops/nearby` | NearbyShopsPage | 按当前校区坐标排序的附近商户列表（复用商家卡片 + 距离角标） |
| `/coupons` | CouponsPage | 全站可用优惠券聚合页（可按领取状态筛选） |
| `/search?kw=` | SearchPage | 搜索结果页（复用 shop-list 的商家卡片） |

> 说明：`/flash`、`/coupons` 两个页面依赖新增后端接口 `GET /coupon/flash/list`、`GET /coupon/list/all`（见 §5.2）。若首期不想动后端，可降级为：抢购 → 跳到"美食"分类下第一个有闪购券的商户，卡券 → 复用 `/merchant/of/type` 列表内的卡片卡券角标。**推荐按 §5.2 加后端接口，成本低收益高。**

### 3.2 校园场景分类宫格（Row 3）

**目标**：替代现有的"城市泛生活分类"，改为校园高频消费场景。一行 5 列，默认展示 **5 个校园核心分类**，点击「更多」横向展开到全部（最多 10 个）。

**推荐校园分类 seed 数据**（`tb_shop_type` 重新灌入）：

| sort | 分类名 | 图标 key | 说明 |
|------|--------|----------|------|
| 1 | 美食 | food | 食堂 / 小吃 / 简餐 |
| 2 | 饮品 | drink | 奶茶 / 咖啡 / 果汁 |
| 3 | 超市 | market | 便利店 / 超市 / 零食 |
| 4 | 打印图文 | print | 打印 / 复印 / 图文 |
| 5 | 快递驿站 | express | 驿站 / 快递代收 |
| 6 | 运动健身 | sport | 健身房 / 球馆 |
| 7 | 自习空间 | study | 自习室 / 图书馆周边 |
| 8 | 数码维修 | repair | 电脑 / 手机维修 |
| 9 | 美发造型 | beauty | 理发 / 造型 |
| 10 | 娱乐休闲 | fun | KTV / 桌游 / 轰趴 |

**数据接入策略（后端不动 + 前端精选，分两步）：**

1. **短期（仅前端）**：分类宫格仍从 `Store.getMerchantTypes()`（`/merchant-type/list`）取数，但前端内置一个 **校园分类映射表**（`{ icon, scene }`），按 sort 重新排序展示前 5，不足 5 个用内置兜底分类补齐。"更多"展开显示全部。
2. **中期（推荐，数据初始化）**：执行 §5.1 的 SQL，把 `tb_shop_type` 更新为校园分类，同时把商户 `tb_shop.type_id` 归并到新分类（旧数据仅保留"美食"映射，其余置为 NULL 或归入对应新分类）。此后分类宫格完全由接口驱动，前端无需映射。

**点击行为**：`goShopList(type)` → `/shops/{typeId}?name={name}`，与现状一致，仅数据变化。

## 4. 视觉与交互规范

### 4.1 设计令牌（复用现有 CSS 变量）

全部使用 `app.css` `:root` 既有令牌，不引入新色值：

| 用途 | 变量 |
|------|------|
| 搜索栏背景 | `var(--color-surface)` + `var(--color-bg)` 搜索框底 |
| 主色（金刚区图标底 / 选中态） | `var(--color-primary)` / `--color-primary-light` |
| 抢购强调色 | `var(--color-accent)`（#ff6633） |
| 签到徽标 | `var(--color-danger)` / `--color-success` |
| 圆角 / 间距 | `--radius-md` / `--space-sm/md/lg` |
| 字号 | `--font-xs`（标签）/ `--font-sm`（按钮文案）/ `--font-md`（搜索词） |

### 4.2 金刚区与分类格样式

- **金刚区格子**：图标外层 `56px` 圆角容器（`--radius-md`），背景用 10% 透明度的主题色（`color-mix(in srgb, var(--color-primary) 10%, transparent)`，需确认目标浏览器支持；不支持则用固定浅色），图标 `24px`，下方 `--font-xs` 文案。
- **分类宫格**：延续现状 `.type-grid` 的 5 列栅格，图标 `48px`，但把图标从"图片 url"改为 **emoji / SVG 图标**（校园场景图无需素材，直接用 emoji，如 🍜🥤🏪🖨️📦）。
- **抢购角标**：金刚区"抢购"格右上角 `⚡` 呼吸动画（CSS `@keyframes pulse`），提示秒杀进行中。
- **签到徽标**：`+N` 使用 `--radius-round` 红色徽标，绝对定位在金刚区「签到」格 📅 右上角；今日已签则置灰显示"已签"。

### 4.3 交互细节

- 搜索面板为**绝对定位浮层**，`z-index` 高于 Feed 流，背景遮罩 `rgba(0,0,0,0.3)`，点击遮罩收起。
- 校区弹层复用**底部弹出**（类似 foot-bar 高度），动画 `transform: translateY`。
- 所有跳转保持 hash 路由；登录态缺失时由路由守卫统一处理（参照 `/chat` 的 `requiresAuth` 模式）。

## 5. 接口契约

### 5.1 数据初始化 SQL（推荐，可选）

```sql
-- 1) 归档旧分类
UPDATE tb_shop_type SET name = CONCAT('[旧]', name), deleted = 1;

-- 2) 灌入校园分类（id 重新自增）
INSERT INTO tb_shop_type (id, name, icon, sort, deleted)
VALUES (1, '美食',   'food',   1, 0),
       (2, '饮品',   'drink',  2, 0),
       (3, '超市',   'market', 3, 0),
       (4, '打印图文','print',  4, 0),
       (5, '快递驿站','express',5, 0),
       (6, '运动健身','sport',  6, 0),
       (7, '自习空间','study',  7, 0),
       (8, '数码维修','repair', 8, 0),
       (9, '美发造型','beauty', 9, 0),
       (10,'娱乐休闲','fun',   10, 0);

-- 3) 商户归并（旧"美食"映射到新 id=1；其余旧分类商户暂归 id=1 或置 NULL）
UPDATE tb_shop SET type_id = 1 WHERE type_id IN (SELECT id FROM tb_shop_type WHERE name LIKE '[旧]%');
```

> 警告：该 SQL 会清掉现有 demo 商户的分类映射，执行前请备份。若不想动数据，跳过本步骤，前端用 §3.2 的"短期映射表"方案。

### 5.2 新增后端接口（推荐，低成本）

| 接口 | 方法 | 说明 | 返回 |
|------|------|------|------|
| `/coupon/flash/list` | GET | 全站**进行中**的闪购券（`status=1`，库存>0），关联商户名/图标 | `List<FlashDealVO>` |
| `/coupon/list/all` | GET | 全站可用优惠券（非闪购 + 闪购均可），可按领取态过滤 | `List<CouponVO>` |

> 若首期不加这两个接口，金刚区「抢购」「卡券」按 §3.1 的降级方案走。

### 5.3 既有接口复用清单（不新增）

| 入口 | 接口 | 参数 |
|------|------|------|
| 搜索-商户名 | `GET /merchant/of/name` | `name`, `current` |
| 搜索-分类直达 / 分类宫格 | `GET /merchant/of/type` | `typeId`, `current`, `x`, `y`（校区坐标） |
| 附近商户 | `GET /merchant/of/type` | `typeId`, `current=1`, `x`, `y` |
| 校园动态 | `GET /post/hot` | `current` |
| 签到 | `POST /user/sign` / `GET /user/sign/count` | - |
| 智能助手 | `POST /agent/chat`（SSE，`/api` 反代） | `message`, `sessionId` |
| 商户分类 | `GET /merchant-type/list` | - |
